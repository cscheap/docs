# 分仓维护与集中发布

日期：2026-10-09。状态：已被 [0002 Git 正文与 CMS 动态读取](0002-git-cms-runtime-content.md) 取代。以下保留早期取舍，不能作为当前实施规则。

## 背景

cs.cheap 的业务分布在 spider、refinery、API 和 frontend。对外文档需要由各业务维护方更新，并统一显示在 frontend 的文档页面中。frontend 已使用 Fumadocs MDX，并有 en、zh-CN、ru 三语言路由。

## 决定

1. 领域正文随业务代码保存在各仓的 `docs/public/`；跨领域教程与统一导航保存在 `cscheap/docs`。
2. docs 用固定来源 SHA 整合内容，发布有摘要和来源记录的内容包；frontend 固定内容包版本后构建。
3. 对外目录按用户任务与概念组织，页面声明文档类型，避免按内部项目划分用户入口。
4. 英文为基准，中文和俄文为译文；保留前端现有语言路由与 introduction 地址。
5. API 参考由客户范围的 OpenAPI 导出生成；说明性内容手写，组件由 frontend 维护。

## 备选方案与代价

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 正文全部集中 docs | 编辑与内容审查简单 | 业务变化需要跨仓配套修改；可作为未来团队分工变化时的调整方向 |
| 各业务仓正文，docs 整合 | 代码与说明同 PR，责任清晰 | 需要版本锁定、整合校验和预览；本项目采用 |
| 正文全部放 frontend | 接入成本最低 | 业务作者需要改 frontend，领域说明易与实现脱节 |
| 仅为文档合并为 monorepo | 同仓原子修改 | 改动现有部署与权限结构的成本超过当前需要 |

构建期内容获取初期采用固定 SHA 检出和导出物，不引入 submodule 的嵌套维护流程。未来可以用发布归档替代检出，但不得改变单一来源和可重复构建的契约。

## 影响

需要维护内容发布链路；文档更新会触发前端构建。正式文档不自动追踪各项目默认分支，业务上线和文档公开需要协调。

文章的稳定 ID 与 URL 分离，公开导航不暴露内部项目结构。公开 docs 仓只接收可公开内容；内部运维资料继续留在各业务仓。

首期不建立独立 CMS、文档专用站点或多版本网站。产品出现同时维护的不兼容 API 主版本时，再按兼容边界设计版本入口，避免按每个服务发布号复制整站。
