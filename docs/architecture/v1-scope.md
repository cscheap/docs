# 首版范围

本页记录用户最新确认的范围，优先于早期的分仓自动整合、前端内容包构建和独立文档站建议。发布模型已于 2026-11-04 由 [ADR 0006](../decisions/0006-content-contract-v3.md) 改为单分支、stage 分频道、KV + R2 交付；下列第 6 条保留为历史表述。

1. 建立 docs 仓库结构。
2. 确认对外文档目录。
3. 建立文档与多语言规范。
4. 根据当前实际能力初始化完整对外正文；用户所说的“日志”已澄清为文档正文。
5. 记录四个项目的 GitHub SHA 等信息，关联正文与代码版本。
6. **历史**：docs 的 preview / master 更新后分别编译并发布到预览 / 生产桶。现行：单分支 `master`，单元 `stage` 决定进入 preview / production 频道，frontend 按频道动态读取，不触发前端整站构建。

## 已确认的维护方式

在项目文档合并到 docs 的机制建立前，由本仓的 AI 代理读取 spider、refinery、api、frontend 并完成所有正文和复核。用户接受前端改造，2026-10-10 确认用 Git 编辑与运行时读取简化内容服务；2026-11-04 确认 Git 仓当 CMS、不要人工审、采集/审核代理用各自定时任务直接写仓。

正文以 Git 为权威来源，英文为主，中文与俄文为翻译。代理直接维护单元文件，不依赖在线编辑器。

## 并行变化

各独立业务变化用独立提交；依赖同一跨项目行为的页面需要联合复核。基线按项目拆分，减少无关文件冲突。

必须区分文件冲突、语义不一致与旧构建覆盖新发布三类问题。单一代理负责文档可以减少作者协调成本，但不能消除业务并行变化；文档必须基于固定 SHA，而不是阅读期间持续变化的工作区。

基线捕获不等于正文已核对，也不证明对应代码已在生产部署。各基线的 documentationReview 为 pending 时不能编译。

## 本期排除

- 多项目 AI 委派与跨仓自动汇总 PR。
- 自动抓最新业务分支并未经核对升级文档。
- 独立对外文档子域名及同域名多应用转发。
- 文档更新触发 frontend 构建或修改 frontend 内容锁。
- 任意 JavaScript / 新 React 组件免前端部署。
- 将内部运维资料和未开放功能直接发布为客户文档。
