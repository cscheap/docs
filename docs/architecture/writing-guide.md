# 对外文档写作规范

目标：让首次使用者完成一次价格查询，再按任务继续；让需要参数和原理的人能直接查阅。默认读者会复制终端命令，但不了解 cs.cheap 的术语、费率引擎和内部项目。英文是主稿，简体中文和俄文保持相同操作与结论。

## 页面分工

| 类型 | 回答的问题 | 推荐结构 |
| --- | --- | --- |
| tutorial | 第一次怎么做成？ | 结果 → 准备 → 编号步骤 → 成功判断 → 常见失败 → 下一步 |
| how-to | 我已接入，怎么完成这个任务？ | 适用场景 → 前提 → 操作 → 验证 → 必要例外 |
| reference | 这个参数或字段是什么？ | 定义、约束、返回、错误；API 参数由生成器维护 |
| explanation | 为什么这样工作？ | 用户问题 → 简单例子 → 原理 → 边界 → 返回操作入口 |

教程不要求先读附录。首次出现 `ask` 时就写“在售报价（`ask`）”，只解释本次操作所需的一句话；计算链、数据归一化、估值方法留在附录。涉及扣费、不可用数据或会改变操作结果的条件必须在操作前说明，不能藏到附录。

## 写法

- 标题写用户要做的事，例如“查询单件饰品”，不要写内部模块名。description 说明读完能做什么，不复制正文第一句或实现细节。
- 首段说明结果及适用场景。操作标题按动作组织；有先后关系的步骤用编号，一步一个主要动作。
- 使用短句、主动语态和日常用词。直接称呼读者，不使用营销保证，不把内部代码名当产品功能。
- 只给一条推荐的初始路径。可选参数、其他语言、复杂分支放在后续操作页或参考链接里。
- 每个教程有可观察的成功条件：HTTP 状态、字段、文件或界面变化。失败表写“看到什么 → 接下来做什么”。
- 页面结尾给一到两个自然的下一步。链接文字说明目标；不要写“点击这里”。
- 代码版本、部署状态、内部表名和采集器部署流程写维护资料；只有影响用户判断的行为写正文。

## 示例

- 默认使用 Bash + curl，不暗示已有 SDK；标明运行环境、前提和占位值。
- 可独立访问的指南要链接密钥准备步骤，并说明 `CSCHEAP_API_KEY` 的来源。请求必须完整，URL 编码饰品名称。
- 初次请求只查询一件饰品，显式选择 `side=ask`。不要用 1000 个名称或全量下载做入门示例。
- 响应示例必须对应已核对的字段。裁剪内容标明“部分字段”；示例金额、时间、ID 不是实时数据，不伪装成功调用。
- 不使用虚构密钥、账号、SDK、免费额度、固定刷新承诺或上线承诺。修改类示例明确哪些 ID 和并发版本需要先读再填。
- 金额带币种，时间带时区，数量和空值分别解释；市场原价与换算金额不能混淆。
- 不把完整 schema 复制进教程，链接生成的接口参考；生成页只改投影和生成器。

## 翻译与复核

先完成英文，再逐页同步中文和俄文，保留相同代码、字段和错误处理。界面名称跟随实际界面；字段、路径和 API Key 等标识不翻译。确认译文语义后再计算整份英文的 sourceDigest。

复核时按读者路径走一遍：能找到入口吗？前提是否齐全？命令能否构造合法请求？成功和失败是否都可判断？下一步是否有链接？未使用真实凭据调用时，只报告静态核对，不能称为线上验收。

运行 `npm run check` 验证结构、频道、链接、翻译摘要和生成参考。不要为纯正文改动运行 frontend 全量构建。
